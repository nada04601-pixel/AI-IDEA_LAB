### 1-1. 인터넷 권한을 두지 않는다

003과 같이 **MVP 앱에는 인터넷 권한(`INTERNET`)을 넣지 않는다.**

- 기기 내 OCR, 저장, 백업, 알림, PDF 모두 인터넷이 필요 없다.
- "이 앱은 인터넷에 연결하지 않아요"를 스토어 설명과 첫 화면에서 약속할 수 있다. 남의 이름·금액을 다루는 앱에서 가장 강한 신뢰 근거가 된다.
- 광고(idea.md 9. 수익 모델)·클라우드 OCR·구글 드라이브 자동 백업은 인터넷 권한이 필요하므로 **후속 단계에서 함께 결정**한다. (7장 미결 사항)

## 2. 데이터 구조 (IndexedDB)

### `people` — 사람

| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (UUID) | 백업 합치기 시 중복 판정에 사용 |
| name | string | 이름. 인덱스 |
| relation | `'family' \| 'relative' \| 'friend' \| 'work' \| 'acquaintance' \| 'other'` | 관계 |
| group | string | 소속·설명 (예: "대학 동기", "○○회사") — 동명이인 구분용 |
| memo | string | 선택 |
| createdAt, updatedAt | number | ms |

### `events` — 행사

| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (UUID) | |
| owner | `'mine' \| 'theirs'` | 내 행사 / 상대 행사 |
| personId | string \| null | 상대 행사일 때 대상 사람 |
| type | `'wedding' \| 'funeral' \| 'firstBirthday' \| 'birthday' \| 'opening' \| 'other'` | 결혼·장례·돌잔치·생신·개업·기타 |
| customType | string (선택) | 직접 입력한 행사 종류 (type이 `'other'`일 때, 예: "칠순"). 합치기에서는 종류가 다르면 다른 행사로 본다 |
| title | string | 예: "내 결혼식", "김민수 결혼식" |
| date | string `YYYY-MM-DD` | 인덱스. 시간대 문제를 피하려고 문자열 저장 (003과 동일) |
| place | string | 선택 |
| remind | boolean | D-day 알림 여부 |

### `records` — 주고받은 내역

| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (UUID) | |
| eventId | string | 어느 행사에서 |
| personId | string | 누구와 |
| direction | `'received' \| 'given'` | 받은 돈 / 준 돈 |
| amount | number (정수, 원) | 금액. 화환·선물처럼 금액이 없으면 0 |
| method | `'cash' \| 'transfer' \| 'flower' \| 'gift' \| 'other'` | 현금·계좌이체·화환·선물 |
| attended | boolean \| null | 참석 여부 (모르면 null) |
| thanked | boolean | 감사 인사 완료 체크 (답례 명단용) |
| memo | string | 선택 |
| source | `'manual' \| 'ocr' \| 'import'` | 입력 경로. OCR 품질 분석용 |
| createdAt, updatedAt | number | ms |

### `settings` — 설정 (키-값)

| 키 | 값 |
|---|---|
| `onboardingDone` | boolean |
| `lastBackupAt` | number \| null |
| `changesSinceBackup` | number — 백업 이후 추가·수정 건수. 홈 백업 카드의 "그 뒤로 N건 추가" 표시와, 0건이면 알림을 생략하는 데 사용 |

## 3. OCR 구현

### 3-1. 처리 구조

```text
[사진 선택/촬영]  @capacitor/camera
      ↓  이미지 파일 경로
[네이티브 OCR]   ML Kit Text Recognition (한국어)  ← 기기 안에서 처리
      ↓  줄 단위 텍스트 + 위치(좌표) + 신뢰도(가능하면)
[웹 코드: 분석]  같은 높이의 글자를 한 줄로 묶기 → 이름 / 금액 / 소속 분리 → 금액 정규화
      ↓
[확인 화면]      원본 이미지와 나란히, 신뢰도 낮은 칸 강조, 사용자 수정
      ↓
[일괄 등록]      records.source = 'ocr'
```

- **네이티브 코드는 "이미지 → 글자와 위치"까지만** 한다. 이름·금액을 나누는 규칙은 웹(TypeScript) 코드에 두어 Vitest로 테스트하고, iOS를 붙일 때도 그대로 재사용한다.
- 금액 정규화 규칙 (예): `100,000` / `100000원` / `10만` / `10만원` / `십만원` → `100000`. 한자 금액(`拾萬`)은 후속.
- 합계·건수는 코드가 계산한다. (001과 같은 원칙)

### 3-2. ML Kit 모델 방식

| 방식 | 앱 크기 | 인터넷 | 비고 |
|---|---|---|---|
| 앱에 모델 포함 (bundled) | 늘어남 (수 MB 단위) `(확인)` | 필요 없음 | 설치 직후 바로 동작. **기본 후보** |
| Play 서비스가 모델 다운로드 (unbundled) | 작음 | 앱 권한은 불필요, 첫 사용 전 다운로드 대기 | 처음 OCR을 쓸 때 모델이 없을 수 있다. |

결정: **앱에 모델 포함** (`com.google.mlkit:text-recognition-korean:16.0.1`) — 사진으로 등록하는 순간이 첫 사용 경험이라 대기·실패가 없어야 한다.

- 결과: 테스트 APK가 약 5MB → **약 25MB**로 커졌다 (모든 CPU 종류의 인식 엔진 포함). Play 스토어에 AAB로 올리면 기기에 맞는 것만 내려받아 실제 설치 크기는 줄어든다.
- ML Kit 라이브러리가 끼워 넣을 수 있는 `INTERNET`·`ACCESS_NETWORK_STATE` 권한은 매니페스트에서 `tools:node="remove"`로 제거하고, **빌드 워크플로가 APK 권한을 검사해 들어 있으면 실패**하게 했다.

## 4. 사전 테스트 (본 개발 전, 1~2일)

OCR은 이 앱의 핵심 차별점이자 Capacitor 선택의 유일한 불확실성이므로 먼저 확인한다.

### 확인할 것

1. **연결 방식**: 한국어 텍스트 인식을 지원하는 Capacitor용 ML Kit 플러그인이 있고 최근까지 관리되는가?
   - 있으면 → 플러그인 사용
   - 없거나 한국어·좌표 정보가 부족하면 → 003의 `WebPrintPlugin.java`처럼 **직접 작은 안드로이드 플러그인 작성** (`TextRecognitionPlugin`, ML Kit 호출 수십 줄 수준)
2. **인식률**: 아래 샘플로 이름·금액이 맞게 읽히는 비율

| 샘플 | 수량 | 목표 `(가정)` |
|---|---|---|
| 은행 앱 이체 내역 캡처 | 10장 이상 | 이름·금액 95% 이상 |
| 엑셀·메모 화면 캡처 | 10장 이상 | 95% 이상 |
| 인쇄 양식 축의금 대장 (손글씨) | 10장 이상 | 측정만 (MVP 포함 여부 판단) |
| 종이 장부·봉투 (손글씨) | 5장 이상 | 측정만 (후속 단계 판단 자료) |

3. **속도·크기**: 저가형 안드로이드 기기에서 1장 처리 시간, 모델 포함 시 APK 크기
4. **신뢰도 값**: ML Kit 결과에서 글자·단어별 신뢰도를 받을 수 있는가 `(확인)` — 확인 화면의 "강조 표시"에 사용. 없으면 금액 형식이 이상한 칸만 강조한다.

### 결과에 따른 판단

- 인쇄 글씨 목표 달성 → Capacitor + 기기 내 OCR로 진행
- 인쇄 글씨도 목표 미달 → 이미지 전처리(자르기·대비) 추가 후 재측정, 그래도 미달이면 클라우드 OCR 도입을 앞당겨 검토 (인터넷 권한 결정과 함께)
- **어느 경우에도 앱 전체를 Flutter 등으로 바꿀 필요는 없다.** OCR은 네이티브 플러그인 한 개로 분리되어 있기 때문이다.

## 5. 내보내기·백업 구현

### 5-1. 백업 파일 형식

```jsonc
// 비밀번호 없음 (기본)
{
  "format": "maeum-jangbu-backup",
  "version": 1,
  "exportedAt": "2026-10-07T09:00:00.000Z",
  "encrypted": false,
  "data": { "people": [], "events": [], "records": [], "settings": {} }
}

// 비밀번호 설정 시
{
  "format": "maeum-jangbu-backup",
  "version": 1,
  "exportedAt": "...",
  "encrypted": true,
  "kdf": { "name": "PBKDF2", "hash": "SHA-256", "iterations": 600000, "salt": "<base64>" },
  "cipher": { "name": "AES-GCM", "iv": "<base64>" },
  "data": "<base64 암호문>"
}
```

- 암호화는 브라우저 내장 **Web Crypto API**만 사용한다. (Capacitor 안드로이드 WebView는 `https://localhost` 보안 컨텍스트라 사용 가능)
- 비밀번호 → PBKDF2로 키 생성 → AES-GCM 256 암호화. AES-GCM은 비밀번호가 틀리면 복호화가 실패하므로 "비밀번호가 맞지 않아요"를 정확히 안내할 수 있다.
- 반복 횟수 600,000회가 저가형 기기에서 너무 느린지 `(확인)` — 2초 이상이면 진행 표시를 넣는다.
- 비밀번호는 어디에도 저장하지 않는다. 분실 시 복원 불가 안내 (idea.md 3-3).
- `version`으로 스키마 변경에 대비한다. 옛 버전 백업도 항상 복원 가능해야 한다.

### 5-2. 복원 (덮어쓰기 / 합치기)

003 `backup.ts`의 `parseBackup` / `mergeEntries` 구조를 확장한다.

| 대상 | 중복 판정 |
|---|---|
| people | id가 같음 → 같은 사람. id가 다르면: 이름과 소속이 모두 같은 사람이 1명이면 자동으로 같은 사람(엑셀 왕복처럼 id가 새로 생기는 경우), 이름만 같으면 **자동으로 합치지 않고** "같은 사람인가요?" 확인 목록으로 (동명이인) |
| events | id가 같음, 또는 type + date + 대상 사람이 같음. 종류를 모르는 내 행사(엑셀에 행사 열 없음)는 같은 날 내 행사가 하나뿐이면 그 행사 |
| records | id가 같음, 또는 행사 + 사람 + direction + amount가 같음 |

- 복원 전에 **미리보기**: 사람 수, 행사 수, 내역 건수, 기간, 중복으로 건너뛸 건수
- 덮어쓰기 전에 현재 데이터를 자동으로 임시 백업해 두고 "되돌리기"를 1회 제공 `(가정)`

### 5-3. 엑셀 (ExcelJS)

| 시트 | 열 |
|---|---|
| 전체 내역 | 날짜, 행사, 행사 종류, 이름, 관계, 소속, 받음/보냄, 금액, 방식, 참석, 감사 인사, 메모 |
| 사람별 장부 | 이름, 관계, 소속, 받은 총액, 준 총액, 차이, 마지막 내역일 |
| 행사별 명단 (행사마다 1시트) | 이름, 관계, 소속, 금액, 방식, 참석, 감사 인사 + 합계 행 |

- 금액 열은 숫자 형식(`#,##0`)으로 저장해 엑셀에서 바로 합계·정렬이 되게 한다. (문자열 저장 금지)
- **가져오기 양식 = "전체 내역" 시트와 같은 열 구성.** 내보낸 엑셀을 고쳐서 그대로 다시 가져올 수 있다. (idea.md 3-3 왕복 편집)
- ExcelJS는 용량이 큰 편이므로 내보내기·가져오기 화면에 들어갈 때만 불러온다(동적 import).

### 5-4. 공유 흐름

003 `backupExport.ts`와 동일:
