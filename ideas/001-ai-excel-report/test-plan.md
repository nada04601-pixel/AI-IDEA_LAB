# 001. AI Excel 보고서 자동생성기

# 테스트계획서

> 기준 문서: `features.md`(인수 조건), `api.md`(오류 코드), `requirements.md`(BR 규칙), `development-plan.md`(Slice)
> `(가정)` 표시는 확인 전 임시 값이다.

---

## 1. 목적과 범위

- **목적**: 이 서비스의 약속은 "정확한 보고서"다. 숫자가 틀리거나, 고객 데이터가 새거나, 남의 파일이 보이면 서비스가 성립하지 않는다. 테스트는 이 세 가지를 최우선으로 막는다.
- **범위**: MVP의 F-001 ~ F-012, API A-01 ~ A-23, 화면 S-01 ~ S-09
- **범위 밖**: 모바일 브라우저, `.xls`, 다중 파일 취합 등 `requirements.md` 7장의 제외 항목

---

## 2. 테스트 원칙

1. **계산은 테스트로 증명한다.** 날짜, 금액, 집계, 합계 검증은 구현보다 테스트를 먼저 쓴다.
2. **자동 테스트는 실제 AI를 호출하지 않는다.** AI 응답은 fixture로 대체한다. AI 품질은 별도의 **평가(eval) 절차**(8장)로 측정한다.
3. **생성된 보고서는 골든 파일과 비교한다.** 사람이 확인한 정답 파일을 기준으로 셀 단위로 비교한다.
4. **보안 테스트는 별도 그룹으로 관리한다.** 권한, 업로드, 데이터 노출은 기능 테스트와 따로 추적한다.
5. **테스트 데이터에는 실제 고객 데이터를 쓰지 않는다.** 실제 양식 기반 샘플은 반드시 마스킹한 뒤 `samples/`에 넣는다.
6. 각 케이스는 **기대 결과가 숫자나 코드로 명확해야** 한다. "정상 동작함"은 기대 결과가 아니다.

## 8. AI 매핑 평가 (자동 테스트와 별도)

자동 테스트는 "AI 응답을 올바르게 처리하는가"를 검증한다. **"AI가 얼마나 잘 맞히는가"는 아래 절차로 따로 측정한다.** 실제 AI를 호출하므로 CI에는 넣지 않고 수동으로 실행한다.

1. **평가 세트 구성**: 서로 다른 컬럼명 체계를 가진 샘플 10개 이상 (가정). 실제 마스킹 데이터, 영문 컬럼, 약어(`금액`, `Amt`, `매출액`), 의미 없는 컬럼명 포함. 각각의 **정답 매핑**을 사람이 작성해 둔다.
2. **실행**: 평가 세트에 매핑 추천을 실행하고 결과를 기록한다. (모델별, 프롬프트 버전별)
3. **지표**
   - 필수 필드 정확도: 정답과 일치한 필수 필드 수 / 전체 필수 필드 수
   - 과잉 매핑률: 대응 컬럼이 없는데 억지로 매핑한 비율 (낮아야 함)
   - 소요 시간, 토큰 수 (비용 추정)
4. **목표치 (가정)**: 필수 필드 정확도 90% 이상, 과잉 매핑률 5% 이하. **현재 기준 문서에 목표치가 없으므로 확정이 필요하다.**
5. **결과 활용**: 모델 선택(소형 vs 상위), `ai_hint` 보강, 프롬프트 수정의 근거로 사용한다. 운영 중에는 `database.md` 8장의 정확도 쿼리(`origin = ai` 비율)로 계속 확인한다.

## 9. 인수 테스트 (UAT) — 실제 양식 / 실제 담당자

`idea.md`의 성공 기준("수작업 결과와 100% 일치")을 확인하는 절차다.

| 단계 | 내용 |
|---|---|
| 1 | 대상 담당자가 **수작업으로 만든 보고서**와 그 원본 데이터(마스킹)를 확보한다. 3건 이상 (가정) |
| 2 | 같은 원본 데이터를 서비스에 넣어 보고서를 생성한다. |
| 3 | 수작업 결과와 생성 결과를 **셀 단위로 비교**한다. (비교 스크립트 작성) |
| 4 | 차이가 있으면 원인을 분류한다: 서비스 오류 / 수작업 쪽 실수 / 규칙 해석 차이 |
| 5 | 담당자가 직접 업로드부터 다운로드까지 수행하는 것을 관찰하고, 막힌 지점을 기록한다. |
| 6 | **소요 시간 비교**: 수작업 소요 시간 vs 서비스 사용 시간. (`idea.md` 2-2 "문제의 크기"를 채운다) |
| 7 | 담당자에게 "다음 주에도 쓰겠는가", "얼마면 쓰겠는가"를 묻는다. (`idea.md` 검증 계획 4번) |

**합격 기준**: 3건 모두 값이 100% 일치(수작업 쪽 실수로 판명된 차이는 제외), 담당자가 도움 없이 완료.

## 12. 결함 관리

### 심각도

| 등급 | 기준 | 예시 |
|---|---|---|
| **Critical** | 숫자가 틀림, 타인의 데이터 노출·접근, 고객 데이터 외부 유출, 서버 장애 | 합계 오차, 다른 사용자 파일 다운로드, AI에 전체 행 전송 |
| **Major** | P0 기능이 동작하지 않거나 우회 불가 | 업로드 실패, 매핑 확정 불가, 생성 파일이 열리지 않음 |
| **Minor** | 기능은 되지만 불편하거나 문구/표시 오류 | 안내 문구 오류, 정렬 문제 |

### 릴리스 기준

- Critical **0건**, Major **0건**
- P0 케이스 전부 통과
- UAT 합격 기준 충족
- Minor는 목록으로 남기고 일정에 따라 처리

### 관리 방식

- GitHub Issues에 `critical` / `major` / `minor` 라벨과 해당 `F-xxx` ID를 기록한다.
- 결함 해결 커밋에는 이슈 번호와 재현 테스트 추가 여부를 남긴다.
